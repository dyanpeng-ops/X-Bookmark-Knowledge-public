## 1. 系统边界、资产与攻击者模型

### 1.1 数据流（不可信输入 → 出站请求）

```text
[X.com 书签]  ← 不可信内容（推文文本 / entities 中的 URL）
      │  上游只读快照 data/upstream/*（fieldtheory）
      ▼
ingest._ingest_links（归一化 / 去重；domain_of）   src/ingest/ingest.py:271（domain_of :65）
      │  写入 external_links 表 —— 此阶段**不做安全判定**
      ▼
xbk links：list_external_links → LinkTarget   src/cli/main.py:606（记录来自 src/database/repository.py:445）
      │  仅搬运已归一化字段，同样**无安全校验**
      ▼
LinkResolver._process            src/external/resolver.py:313
      │  scheme 白名单 / skip_domains / max_links_per_tweet / attempts 上限
      ▼
HttpFetcher.__call__             src/external/fetcher.py:449
      │  每一跳：_guard(url) → transport(url) → 若 3xx 则 urljoin 后循环
      ▼
UrllibTransport (urllib)         src/external/fetcher.py:292
      │  不跟随重定向；单次请求；受 timeout / max_bytes 约束
      ▼
socket.getaddrinfo → connect    ← ★ 本模型的核心薄弱点（见 T2）
      ▼
handlers/*.extract → 正文 → 写 knowledge/**/assets/.../links/*.md → 落库
```

### 1.2 资产（要保护什么）

| ID | 资产 | 被 T1–T4 触及的后果 |
|---|---|---|
| A1 | 本机 / 内网 HTTP 服务（admin 面板、开发服务器、内网 API） | 响应正文被写入知识库 Markdown（`AGENTS.md` §6 红线） |
| A2 | 云实例元数据端点（`169.254.169.254`、`metadata.google.internal`） | 临时凭据被写入 Markdown / 日志（最严重） |
| A3 | 本机文件系统 | `file://` 已由 scheme 白名单排除（见 T1 已防项） |
| A4 | 知识库产物完整性 `knowledge/**` | 内容注入、伪造来源（误导后续 AI 分析） |
| A5 | 本机时间 / 带宽 / 连接数 | 单个恶意书签即可长时间占用同步任务（T4） |
| A6 | 状态库 `data/**/*.db` | `error_message` 只写异常文本与 URL，不写响应正文（现状安全，记为不变量） |
| A7 | 出站请求本身 | 把本项目当跳板放大攻击第三方（T4 放大） |

### 1.3 攻击者能力（范围限定）

**具备**：
- 完全控制被收藏推文中的任意 URL（含后续被收藏即可生效）；
- 完全控制自有域名的 **DNS 应答**（TTL 可设 0，可先公网后内网）；
- 完全控制其服务器的 HTTP 响应头、正文、状态码与**重定向链**；
- 可对每次请求采用慢速（drip）响应；
- 只能做**盲 SSRF**（知识库在本地，默认读不到回显），但可通过"内容是否被收录/是否报错"做侧信道推断。

**不具备 / 不在范围**：
- 无本地代码写权限、无配置修改权限、无运行账号权限；
- **不做真实内网探测**：本文件与后续测试**只**使用离线 fake resolver / fake transport 与文档专用地址段（`192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`）构造用例；
- 供应链攻击、上游 `fieldtheory` 数据投毒、有本地权限的攻击者 → **不在 D-6 范围**（不扩无关模块）。

### 1.4 已防项：`netguard.py` 现状能力（先读懂它）

| 能力 | 位置 | 效果 |
|---|---|---|
| 22 个非公网网段黑名单 | `netguard.py:44-70` | RFC1918 / CGNAT / 回环 / 链路本地（含元数据）/ 保留 / 文档段 / 多播 + IPv6 等价集合 |
| IPv4-mapped IPv6 归一 | `netguard.py:90-91` | `::ffff:127.0.0.1` 按 `127.0.0.1` 判定 |
| IP 字面量直接判定 | `netguard.py:132-136, 147-153` | 不经 DNS 即拦 |
| **主机名 → 解析全部地址，任一非公网即拦** | `netguard.py:138-143` | 覆盖"域名解析到内网"，且是**从严**策略（避免多 A 记录择一绕过） |
| 显式白名单（精确 / 子域） | `netguard.py:95-107, 127-128` | 放行自建服务；命中即跳过 DNS 与判定 |
| **初始请求 + 每一跳重定向后复核** | `fetcher.py:458`（`_guard` 定义 `:493-511`） | 排除"首跳公网、次跳内网"的经典绕过 |

| 默认开启 | `config.py:260` + `config/config.example.yaml:114` | `external.block_non_public_hosts: true` |

> **结论**：`netguard.py` 的**判定逻辑**（T1 的核心）质量高，攻击面已被压到"判定与连接之间的时间窗"与"边界完备性"。**这也是本文件把 T2 而非 T1 列为首要问题的原因。**

## 2. D1 — 四类威胁：攻击路径与缺口

严重度口径：**高** = 可直接导致 A2/A1 泄露或长时间 DoS；**中** = 需特定条件或仅放大；**低** = 加固收益有限。

### T1 SSRF

**攻击路径**：恶意书签 URL → `list_external_links` → `LinkResolver` → `HttpFetcher._guard` 判定 → `UrllibTransport` 连接。
若判定被绕过，正文即被写入 `knowledge/**/links/*.md`（A4），或元数据凭据入 Markdown（A2）。

**已防**：见 §1.4 全表。特别地，"主机名解析出**任一**非公网地址即拦"（`netguard.py:141-143`）已封死最常见的"域名指向 127.0.0.1"。

| 缺口 | 位置 / 依据 | 严重度 | 说明 |
|---|---|---|---|
| **G1-1 判定与连接之间存在解析时间窗** | `netguard.py:138`（解析）→ `fetcher.py:523-528`（`urllib` 再次独立解析） | 中（T2 本体为高） | 即 SEC-01 本体，详见 T2 |
| **G1-2 网段黑名单不完备** | `netguard.py:44-70` 未见下列段 | 中 | 缺失：`192.88.99.0/24`（6to4 中继，已弃用）、`2002::/16`（6to4，可内嵌私网 v4）、`2001::/32`（Teredo）、`::/96`（IPv4-compatible，如 `::127.0.0.1`）、本地 NAT64 `64:ff9b:1::/48`（仅 Well-Known `64:ff9b::/96` 已列）。**是否真能路由到内网取决于主机/IPv6 配置 → `待验证`** |
| **G1-3 数值型主机写法依赖解析器一致性** | `netguard.py:132-136, 147-153` | 中 | `ipaddress.ip_address("2130706433")` / `"0x7f.1"` / `"0177.0.0.1"` **不**被识别为字面量，故落入 `resolver(host)`；若解析器与 `urllib` 对同一字符串的理解不一致（`urlsplit` 与 `urllib` 是**两套**解析代码），即为绕过。现用系统解析器时应一致，但**属隐式假设 → `待验证`** |
| G1-4 无端口策略 | `fetcher.py:449` 起未限制端口 | 低 | 公网 IP 的非标准端口（如 25/6379）仍可被访问；属纵深防御，非内网绕过 |
| **G1-5 默认 opener 会走环境变量代理** | `fetcher.py:284-289`；已核实 stdlib `build_opener` 的 `default_classes` **含 `ProxyHandler`**（未传入同名子类，故不会被跳过） | 中 | 当容器/环境设置了 `HTTP_PROXY`/`HTTPS_PROXY` 时，真正的连接由**代理**发起；`netguard` 校验的"目标主机 IP"与**实际连接的对端**不再同一主体，T2 的 IP 绑定方案也会退化为绑定代理地址。**结论依据 stdlib 源码（已读）** |
| G1-6 `allow_hosts` 通配符写法有放宽陷阱 | `netguard.py:102` `lstrip("*.")` | 中（配置项） | 条目 `"*.com"` / `".com"` 归一后为 `com`，导致**所有 `.com` 域被放行**；`netguard.py` 不校验条目合法性，`config.py:440`（`_as_str_tuple`）也不校验。属"误伤=放宽安全"。注：`lstrip("*.")` 会剥掉**全部**前导 `*`/`.`，故 `"**evil.com"` 亦归一为 `evil.com`（比两个示例更宽） |
| G1-7 关闭开关是静默的 | `fetcher.py:499-500` 提前 return，无 `logger.warning` | 低 | `block_non_public_hosts: false` 时无任何提示，误配不可见 |
| G1-8 DNS 失败被当作瞬时错误重试 | `fetcher.py:508-509` → `TransportFailure` | 低（DoS 见 T4） | 语义正确，但与 T4 的放大叠加 |

### T2 DNS rebinding（SEC-01 本体）

**攻击路径**：
1. 攻击者域名 `evil.example` 首次 A 查询返回公网 IP（如 `192.0.2.10`）；
2. `HttpFetcher._guard` 调用 `check_url_allowed` → `system_host_resolver`（`netguard.py:76-80`）→ 判定**公网，放行**；
3. `UrllibTransport` 调 `urllib` → `socket.create_connection` **再次独立 `getaddrinfo`**；
4. TTL=0 时第二次应答可为 `127.0.0.1` / `169.254.169.254` → **连接内网**，判定从未生效。

**已防**：**无**。逐跳复核（`fetcher.py:458`）不能覆盖此窗，因为窗口在**单次请求内部**（同一跳的判定与连接之间）。

| 缺口 | 依据 | 严重度 |
|---|---|---|
| **G2-1 无 IP 绑定（TOCTOU）** | `netguard.py:138-143` 与 `fetcher.py:523-528, 326` 之间无绑定；`urllib` 自行解析 | **高** |
| G2-2 静态二次解析也仅缩小窗口 | 同上 | 方案 2B 的固有局限 |
| G2-3 IP 绑定方案与"多地址/HTTPS/重定向"的兼容要求 | `fetcher.py:284-289`（`HTTPSHandler` + 默认 context）、`:461-479`（逐跳） | 需在实现阶段逐项处理（SNI/Host 保留、证书校验、多已验证地址回退、代理已禁） |

**红队直觉**：证明"防住了"的**唯一硬证据**不是"又解析了一次"，而是**实际连接的对端 IP 必须是已通过判定的那个 IP**。这直接决定 D3 的断言写法（见 §4 T2 用例）。

### T3 重定向绕过

**攻击路径**：首跳公网 URL → 3xx `Location` 指向内网 / 非 http(s) → 若复核缺失或只查首跳即被绕过。

**已防**（实现质量高）：
- 显式逐跳跟随（`_NoRedirectHandler`，`fetcher.py:277-289`），3xx 不自动跟随；
- **每一跳前**重新 `_guard`（`fetcher.py:458`）；
- `Location` 缺失 → `TooManyRedirectsError`（`:463-466`）；
- 跳数上限（`:467-471`）；
- 跳后 scheme 复核（`:474-477`）；
- 相对 `Location` 用 `urljoin` 正确解析（`:473`）；
- 既有测试：`tests/test_external.py:283, 297, 312, 325, 332, 1345`。

| 缺口 | 位置 / 依据 | 严重度 | 说明 |
|---|---|---|---|
| **G3-1 3xx 响应正文被完整读入** | `_read_response` 对所有状态码都读至 `max_bytes`（`fetcher.py:360-390`，3xx 分支 `:461-479` 丢弃正文） | 中 | 每跳最多 5 MB 无用传输，最坏 6 跳 ≈ 30 MB / URL（与 T4 放大叠加）。修法：3xx 正文限读一个小上限 |
| G3-2 允许 HTTPS→HTTP 降级且无提示 | `fetcher.py:474-477` 只查 scheme 是否允许 | 低 | 仅机密性问题；当前**不发送** `Authorization`（见 G3-3） |
| G3-3 跨源重定向不携带凭据（现状安全，需锁定为不变量） | `fetcher.py:318-323` 请求头仅 UA/Accept/Accept-Encoding/Accept-Language | —（安全属性） | 未来若加入 `Authorization`/Cookie，必须补"跨源剥离"；建议写成不变量注释 + 回归用例 |
| G3-4 `Location` 含 userinfo / 畸形写法的解析一致性 | `netguard.py:123-124` 取 `urlsplit().hostname`；`urllib` 另有一套解析 | 低–中 | 与 G1-3 同源问题：两套解析器的一致性属隐式假设 → `待验证` |
| G3-5 仅按次数防环，无"已访问 URL"记忆 | `fetcher.py:467-471` | 低 | 已由上限兜住；仅影响无谓请求数（计入 T4 预算） |
| G3-6 `300`/`304` 不在重定向集合内 | `fetcher.py:75` | —（偏安全） | 会被判为失败而非跟随，属可接受行为，建议写入文档 |
| G3-7 无"重定向仅限初始 host"策略 | — | 低 | 见方案 3B（更严策略，副作用是误伤合法 CDN 跳转） |

### T4 资源耗尽（大文件 / 慢连接 / 连接数）

**攻击路径**：恶意服务器用超大响应、慢速 drip、无限重定向/重试链，把一个书签变成长时间/大流量的资源黑洞（A5），并放大为对第三方的请求（A7）。

**已防**：

| 能力 | 位置 | 说明 |
|---|---|---|
| 单页体积上限 5 MB | `config.py:224, 251`；`fetcher.py:373-390` | **先看 `Content-Length` 超限则不读正文**；否则最多读 `max_bytes + 1` 字节 |
| 单次 socket 超时 20s | `config.py:225`；`fetcher.py:326` | 连接与每次读操作分别受限 |
| 重试有限 + 线性退避 | `fetcher.py:518-556`；`config.py:248-249` | 总尝试 = `1 + retries` = 3；退避 = `backoff × 第几次` |
| 重定向跳数上限 5 | `config.py:228`；`fetcher.py:467` | 循环有界 |
| 每推文外链上限 10 | `config.py:250`；`resolver.py:316-319` | 超限记 `SKIPPED` |
| FAILED 累计尝试上限 3（需 `--force`） | `config.py:255`；`resolver.py:336-345` | 跨运行不无限重打 |
| 相邻请求礼貌间隔 1s | `config.py:256`；`resolver.py:347-349` | 天然限速 |
| **串行执行（无并发）** | `resolver.py:270-309` 单线程循环 | 连接数恒为 1 —— 这是"连接数"威胁当前被天然挡住的原因 |

| 缺口 | 位置 / 依据 | 严重度 | 说明 |
|---|---|---|---|
| **G4-1 无总墙钟时限（慢连接）** | `fetcher.py:326` 传入的是**逐操作** socket 超时；`:382` 一次 `read()` 内部多次 `recv`，每次都以 20s 为界 | **高** | 服务器每 <20s 发 1 字节即可让单次抓取**无限期**占用任务；20s 超时不会触发。**"慢连接"明确属 D-6 范围** |
| **G4-2 DNS 解析无超时** | `netguard.py:79` `socket.getaddrinfo`（stdlib 无 timeout 参数），发生在任何 socket 超时生效**之前** | 中–高 | 恶意/故障 DNS 可造成长时间阻塞；`fetcher.py:508` 只处理"解析失败"，不处理"解析挂起" |
| **G4-3 请求数与流量放大（可量化）** | `(1+retries) × (1+max_redirects)` = 3 × 6 = **18 请求 / URL** | 中 | **上界**墙钟 ≈ 18 请求 × 20s + 退避（每跳最多 2 次、共 9s；6 跳共 54s）≈ **7 分钟 / URL**（达成条件苛刻：6 跳各用满 3 次请求、且每次响应耗时逼近 20s）；×10 链接 ≈ **70 分钟 / 推文**；流量 ≈ 18 × 5 MB = **90 MB / URL**（叠加 G3-1 后 3xx 正文也计入） |
| G4-4 错误/重定向路径同样读满 `max_bytes` | `fetcher.py:360-390` | 中 | 与 G3-1 同一根因 |
| G4-5 无每主机熔断 / 同轮失败记忆 | `resolver.py:336-345` 仅跨运行计数 | 中 | 同一死主机在**同一轮**内被每条链接各打 3 次 |
| G4-6 无整轮总请求预算 | — | 低 | 上游推文数有界，但"每推文 10 × 每 URL 18"无全局上限 |
| G4-7 串行是当前安全属性，需锁定为不变量 | `resolver.py:270-309` | —（不变量） | 若未来引入并发（`ThreadPoolExecutor`），连接数上限随之消失，必须同时引入信号量；建议写入 `resolver.py` 模块注释 |
| G4-8 压缩炸弹当前不适用 | `fetcher.py:321` `Accept-Encoding: identity`；stdlib 不解压 | —（明确不做） | 若未来支持 gzip/br，需重新评估解压比上限 |

## 3. D2 — 方案比较（每类 ≥ 2 种；含代价 / 覆盖度 / 误伤率）

> **本节只给"建议方案"，不做最终路线选择。** 误伤率 = 合法抓取被误拦/体验受损的概率。

### T1 SSRF

| 方案 | 做法 | 代价 | 覆盖度 | 误伤率 | 备注 |
|---|---|---|---|---|---|
| **1A 补网段 + 解析一致性** | 在 `BLOCKED_NETWORKS` 补 `192.88.99.0/24`、`2002::/16`、`2001::/32`、`::/96`、`64:ff9b:1::/48`；统一"用于判定"与"用于连接"的主机解析口径 | 低（~25 行 + 用例） | 中（补边界，不动架构） | 极低 | 不改调用方；风险最小 |
| **1B 1A + 配置护栏** | 1A 之上：`allow_hosts` 条目校验（拒 `*.com` 之类纯 TLD/空标签，或要求显式 `*.` 前缀语义）；关闭开关时 `logger.warning`；端口策略（默认仍不限，可选白名单）；**代理策略显式化**（默认禁用 env 代理或落日志告警） | 中（~60 行 + 用例 + 配置文档） | 中–高 | 低（端口白名单可能误伤合法非标端口站点） | **建议采用**；代理项触及 `fetcher.py:284-289` |
| 1C 网络层 egress（防火墙 / 容器策略 / 独立低权用户） | 在部署侧限制出站 | 高（跨平台、运维交付物） | 最高 | 取决于运维 | **不在本项目范围**（D-6 明确"不扩无关模块"）；建议记为**外部补偿控制需求**，不纳入代码改造 |

**建议**：**1B**（其中网段补齐按 G1-2 的 `待验证` 结论决定是否全补）；1C 仅作为部署建议写入文档。

### T2 DNS rebinding

| 方案 | 做法 | 代价 | 覆盖度 | 误伤率 | 备注 |
|---|---|---|---|---|---|
| **2A 绑定已验证 IP + 保留 SNI/Host** | 自定义 `HTTP(S)Connection.connect()`：用已通过 `netguard` 的 IP 连接；HTTPS 用 `ssl_context.wrap_socket(sock, server_hostname=原host)` 保留 SNI 与证书校验；保留 `Host` 头；多已验证地址可回退 | 中（估 **60–100 行** + 传输层测试；与 `docs/X-Bookmark-Knowledge-Phase9-Report-2026-10-09.md:82` 的既有估算一致） | **高（根治 TOCTOU）** | 中低：多 A 记录/CDN 需正确回退；代理场景须先禁代理（G1-5） | **建议采用**；必须与 G1-5 一并处理，否则绑定的是代理地址 |

### 4.2 T2 DNS rebinding 用例（**红队核心**）

| ID | 场景 | 断言（证明防住） | 红队/反证 |
|---|---|---|---|
| **RB-01** | resolver 桩：第 1 次返回公网 IP，第 2 次返回 `127.0.0.1`；transport 桩记录"被要求连接的地址" | **断言实际连接的对端 = 第 1 次已验证的公网 IP**，且 `127.0.0.1` 从未出现 | **关键反证**：把实现回退为"传 hostname 给 socket" ⇒ transport 桩观测到 hostname/第二次解析 ⇒ 用例必须失败 |
| RB-02 | 同上，但走 HTTPS | 断言 `server_hostname` = 原 host（SNI 与证书校验保留），对端 IP = 已验证 IP | 去掉 `server_hostname` ⇒ 失败（并会触发证书校验问题） |
| RB-03 | 多已验证地址，首个连接失败 | 断言回退到**另一个已验证**地址，且绝不回退到未验证地址 | 允许回退到未验证地址 ⇒ 失败 |
| RB-04 | 重定向后再发生 rebinding | 每跳都绑定**该跳**已验证 IP（验证 `_guard` 与绑定成对出现） | 改回"仅首跳绑定" ⇒ 失败 |
| RB-05 | 代理开启时 | 断言要么代理被禁用，要么明确记录"绑定不适用于代理路径"（策略先行） | 与 SSRF-06 联动 |
| RB-06 | 解析次数守卫 | 断言每个 URL 的解析次数 ≤ 预期（如 2），防止"绑定后又解析"的伪修复 | 每次连接都解析 ⇒ 失败 |

### 5.5 回滚方案

- 全部改动集中在 `src/external/**` + `src/config.py` + `config/config.example.yaml` + `tests/**`，**不改数据库结构、不动知识库**；
- 新限额均有配置默认值，可用 `block_non_public_hosts: true` 等既有开关回退；
- 若 2A 引入回归：保留 2B/2C 作为降级路径（同一 PR 内可切换），或 `git revert` 单次提交；
- **不触碰** `data/**`、`knowledge/**`，无需数据回滚。

### 5.6 明确不做（红线）

1. **不探测真实内网 / 不做真实 SSRF 验证**（仅离线桩 + 文档专用地址段）；

4. 不修改上游只读数据与用户知识库；
